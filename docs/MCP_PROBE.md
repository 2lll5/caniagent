# MCP stdio behavior probe

`npm run probe:mcp -- --output=artifacts/mcp-probe.json` runs an opt-in behavior probe for the MCP client row in the compatibility matrix.

The probe creates a temporary workspace and home for each supported agent, configures a dependency-free local stdio MCP server named `caniagent_echo`, records the installed agent version, and asks the agent to call the echo tool with a deterministic marker. Temporary files are removed after each run. It does not modify the developer's normal agent configuration.

## Verdicts

- `pass`: the agent command succeeded and the local MCP server recorded exactly one post-initialization `tools/call` attempt, for the expected echo tool with exactly the expected string `text` argument and no extra fields (matching the advertised `additionalProperties: false` input schema). The marker appearing in CLI stdout/stderr alone is **not** evidence: the prompt already contains it.
- `fail`: the agent command succeeded, the local MCP server completed `initialize` and received a valid `notifications/initialized` notification, but the server observed zero, rejected, or repeated `tools/call` attempts instead of exactly one valid call. This does not, by itself, prove the agent lacks MCP support.
- `skip`: the agent executable was not installed.
- `inconclusive`: execution failed, timed out, was interrupted, the MCP server never completed `initialize` plus the required `notifications/initialized` notification (for example, because the CLI ignored or rejected its fixture configuration), or trustworthy receipt evidence was unavailable. Authentication-dependent and configuration failures therefore do not become negative compatibility claims.

The JSON evidence records platform, Node version, agent version command, exact redacted execution command, exit status, redacted/truncated stdout and stderr, and a `serverInitialized` handshake indicator plus the number of server-recorded `tools/call` attempts, including rejected attempts. The initialization indicator requires both a structurally valid JSON-RPC MCP `initialize` request (request ID, protocol version, capabilities, and client information) and a subsequent valid `notifications/initialized` notification without a request ID. A missing, premature, or malformed notification cannot establish handshake evidence. Optional notification `params` and its optional `_meta` must be JSON objects when present (per the MCP notification schema); malformed values cannot establish handshake evidence. Tool calls received before a valid initialization are rejected with JSON-RPC server error `-32000`, counted as rejected attempts, and cannot produce a matching receipt even when their arguments are correct. Malformed JSON-RPC `tools/call` envelopes (missing or invalid request ID or protocol version) also count as rejected attempts, never as successful tool use. The private receipt lives only in the temporary fixture, contains the fixed expected tool name (or null for an unknown name) and a boolean argument match (never caller-provided tool names or arguments), and is deleted after classification. A syntactically valid JSONL receipt with invalid record structure (missing/extra fields, wrong types, impossible name/match combinations, duplicate JSON keys, or noncanonical serialization), a malformed JSONL file, or an oversized receipt is inconclusive; such infrastructure evidence must never be treated as a negative MCP result. Do not promote `data/matrix.json` claims from a single inconclusive run; retain reproducible probe artifacts and the tested agent version.

The server creates an empty receipt file at successful handshake completion, before writing the initialization marker. An existing empty receipt is evidence of zero tool calls; a missing receipt file is **inconclusive**, not a zero-call `fail`. This avoids misclassifying missing or lost receipt evidence as a negative MCP result. A server crash after handshake may still require additional investigation; this check is not a guarantee against all filesystem failures.

Malformed JSON alone produces JSON-RPC `-32700` and the server continues processing later requests. Receipt write failures are infrastructure errors and must not be disguised as JSON parse errors; the server exits unsuccessfully instead of fabricating a protocol response.

The stdio server returns JSON-RPC `-32600` for valid JSON that is not a request object (such as `null` or arrays), and for malformed `tools/list` request envelopes. A structurally valid `tools/list` is served only after the legacy `notifications/initialized` handshake; requests before that point receive `-32000` rather than an advertised tool list. These messages do not become tool-call receipts; a subsequent valid post-handshake request is still processed.

The fixture implements the legacy `2025-06-18` MCP handshake. Its `initialize` response always advertises that supported revision rather than echoing an arbitrary client-supplied version; a client that cannot negotiate it should disconnect, leaving the probe `inconclusive`. It does **not** implement the modern `2026-07-28` stateless `server/discover` protocol, so modern-only clients cannot be certified by this probe. This is a probe limitation, not a compatibility claim. See the [legacy lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle) and [modern versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) specifications.

## Isolation and credentials

The MCP server itself requires no network access, API key, package install, or external service. Agent execution may still require the provider's normal authentication and may consume provider quota. The probe redirects `HOME`, `USERPROFILE`, and XDG config/data/state paths to temporary directories. Output passes through the shared probe redactor before it is persisted.

The generated configurations use the documented project/user configuration surfaces for Codex, Claude Code, Gemini CLI, and OpenCode. Because those CLIs evolve independently, a configuration parse failure should remain `inconclusive` until the adapter is updated and re-tested.
